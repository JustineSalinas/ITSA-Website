1. Why this website exists

The ITSA website is the organisation's official public face. It has three jobs, in order of importance:

  1. Recruit. Turn an interested IT student into a member.
  2. Inform. Tell members what is happening and when.
  3. Prove we are real. Show a live, organised group run by actual people.

The third job is quiet but decisive. A prospective student decides in under a minute whether ITSA looks like a serious organisation. Empty pages, stale event lists, or a site that feels sloppy work against us — so does a site that loads slowly on a cheap phone using campus wifi.

One sentence to keep in mind: because this is an IT students' organisation, the website itself is the portfolio. If it is well made, that is the argument. Nothing else on the page will convince anyone otherwise.

3. User flows

Three journeys matter. Each is written as the steps a real person takes, with the points where things can go wrong called out — those are where we lose people.

3.1 Flow A — A prospective student joins (the most important flow)

  1. Arrives on the Home page — usually from an Instagram or Facebook link, or by typing the address at an org fair. On a phone.
  2. Scans the hero section and learns in a few seconds what ITSA is.
  3. Looks for proof. Scrolls past highlights, upcoming events, and the officers preview. This is the credibility check.
  4. Optionally explores — taps Events, Officers, or Projects to see whether anything is actually happening.
  5. Taps "Register Now" and lands on the Join page.
  6. Fills in the form — name, email, and a message. Student ID and year level are optional so the form never feels like paperwork.
  7. Submits and immediately sees a confirmation that the message was sent.
  8. Behind the scenes: the message is emailed to the ITSA inbox, and an officer follows up.
Where this flow breaks today
  • The site is slow to load. Large images cost us visitors on campus wifi before they see anything.
  • Events look empty or out of date. A stale events page actively damages the credibility we are trying to build.
  • The follow-up never happens. Submissions only become an email. If nobody checks the inbox, the student hears nothing and we lose them. See FR-24.

3.2 Flow B — A member checks an event

  1. Opens the site and goes straight to Events.
  2. Sees upcoming events first, separated from past ones, newest first.
  3. Taps an event for the full details — date, time, venue, and description.
  4. Gets the answer and leaves. Success here is speed, not time on site.
Design note

Members are repeat visitors who want one fact. Every extra tap between the home page and an event date is a small failure. Nothing on this path should require signing in.

3.3 Flow C — An officer publishes an event

  1. Goes to /admin and is sent to the sign-in page.
  2. Signs in with the email and password issued to them.
  3. The system checks two things: that the password is correct, and that this account has been approved as an officer. Both must pass — a correct password alone is not enough.
  4. Lands on the dashboard showing how many events and officers exist.
  5. Opens Events and fills in the form — title, date and time, venue, description, and an optional image.
  6. Saves. The event appears on the public site immediately.
  7. Behind the scenes: the change records who made it and when.
  8. Signs out, which fully ends the session — important on shared campus computers.
Two deliberate rules
  • Nothing is ever truly deleted. Removing an event hides it rather than destroying it, so a mistake can be undone.
  • Sessions expire after about eight hours, so a forgotten sign-in on a lab computer does not stay open.

4.4 Ideas not yet agreed

These appear on the progress tracker without an agreed scope. Each needs a decision before any work starts — see the SPMP for who decides and by when.

IdeaThe question to answerRecommendation
News feed How is this different from Events? Who writes the posts, and how often? Only build it if someone commits to posting weekly. An empty feed is worse than no feed.
Metrics landing page Which numbers, and who is the audience — officers, or the public? Define the numbers first. If it is for officers, it belongs in the admin area, not the public site.
Chatbot What questions must it answer that a good FAQ page could not? Try a short FAQ first. It is far cheaper and answers the same questions.
Push notifications Marked "not applicable / unsure" on the tracker. Drop it. Notifications need visitors to opt in and an app-like setup; almost nobody accepts. Announce through Facebook and email instead.

5. Quality requirements

These are not features, but the site fails without them.

5.1 Speed

IDRequirementStatus
NFR-1The home page is usable within about 3 seconds on a mid-range phone over campus wifi.Needs testing
NFR-2No single image is larger than it needs to be for how it is displayed.Open
NFR-3Pages do not shift around while loading.Needs testing

Live issue against NFR-2. The logo files currently add up to roughly 936 KB, replacing a version that was 1.4 KB — and one of the three files is not used anywhere. Because browser tab icons are not automatically optimised, visitors download the full file. This is the single easiest speed win available to us.

5.2 Accessibility

IDRequirementStatus
NFR-10Text has enough contrast against its background to be readable in sunlight.Needs review
NFR-11Everything works with a keyboard alone, and the focused item is always visible.Needs review
NFR-12Visitors who ask their device to reduce motion get a still version of the site.Open
NFR-13Meaning is never carried by colour alone.Needs review
NFR-14Images have text descriptions for screen readers.Done

Target: WCAG 2.1 Level AA — the standard most schools and public institutions expect. NFR-12 is currently failing: the smooth-scrolling effect applies to everyone, including visitors who have asked their device not to animate.

5.3 Security and safety

IDRequirementStatus
NFR-20Only approved officers can change any content. Being signed in is not enough on its own.Done in code
NFR-21The rules protecting the database are actually deployed, not just written.Blocking
NFR-22The join form cannot be used to flood our inbox or run up costs.Done
NFR-23The site cannot be embedded inside another site to trick officers into clicking.Done
NFR-24Passwords and secret keys never appear in the code or in the public repository.Done
NFR-25Only our own image storage can supply pictures, so pages cannot quietly report visitors to outside servers.Done
NFR-26Data is backed up on a schedule, so a mistake or an accident is recoverable.Open
NFR-27Only our own website can talk to our database — not a script someone writes.Open

NFR-21 is the one urgent item in this document. The protective rules exist in the code and have been tested, but they are a separate switch that must be turned on for the live database. Until someone does that, the live site still accepts changes from any signed-in account.

Because the repository is public, the current weak rule is readable by anyone. The SPMP lists this as the first task, and the order matters: approve an officer account before switching the rules on, or everyone is locked out — including us.

5.4 Reliability and upkeep

IDRequirementStatus
NFR-30If the database is unreachable, the problem is visible to us rather than hidden behind stale content.Done
NFR-31Content changes do not require a developer or a code change.Partial
NFR-32Automated checks run before any change reaches the live site.Done
NFR-33The site keeps working when this year's officers graduate.Open

NFR-31 is only partly met: the 19 officer profiles are still written into the code, so updating the roster each year currently needs a developer. It should be a form. NFR-33 is the long-term risk the SPMP addresses directly.

6. Assumptions and limits

  • Members do not get accounts. Only officers sign in. This is a deliberate simplification — member accounts would roughly double the work and the risk.
  • The site is in English only.
  • We rely on Firebase and Vercel. Both have free tiers that suit our size, but both are outside our control.
  • Payments, dues collection, and voting are out of scope for this version.
  • Event attendance and RSVP are out of scope for this version, but the design should not make them harder later.

7. How we will know it is finished

This version is complete when all of the following are true:

  1. Every Must requirement above is done and checked.
  2. The protective rules are live on the real database, and at least two officers can sign in.
  3. An officer who is not a developer can publish an event without help.
  4. The home page loads acceptably on a mid-range phone on campus wifi.
  5. Someone other than the author has reviewed the site with a keyboard only, and for colour contrast.
  6. A written handover note exists, explaining who holds which account.
