3. How we work

We had one incident worth learning from: a large change went straight onto the live branch without review, and it contained a mistake that stopped the website from building. Nobody noticed for a day, and no new version could be published in the meantime. The process below exists to prevent a repeat — it is not bureaucracy, it is the cheapest possible insurance.

3.1 The rules

  1. Never work directly on main. main is what the public sees. Create a branch for your work.
  2. Open a pull request. This is how you propose your change and how others see it.
  3. Wait for the automatic checks. They run in about 90 seconds and catch broken builds, broken security rules, and known-vulnerable packages.
  4. Get one review. Any teammate. A quick look is enough — the goal is that two people have seen it.
  5. Merge, then check the live site. Publishing happens automatically after merging.

3.2 What the automatic checks cover

CheckWhat it catches
Code styleObvious mistakes and unused code
BuildAnything that would stop the site publishing — the exact failure we hit
Security rules (21 tests)Any change that would let a non-officer edit the site
Package safetyKnown security holes in the code we depend on
Preview deploymentGives every pull request its own working link to click through before merging

Recommended setting change (task A4). These rules currently rely on everyone remembering. Turning on "branch protection" for main in the repository settings makes the pull request and passing checks required — the mistake above becomes impossible rather than merely discouraged. It takes two minutes and needs no code.

3.3 When is something "done"?

A task is done when all of these are true — not when the code is written:

  • It works on a phone as well as a laptop.
  • The automatic checks pass.
  • Someone else has looked at it.
  • It has been clicked through on the live site after merging.
  • The tracker row has been updated with the date.

7. Risks

RiskHow likelyWhat happensWhat we do about it
The database rules never get switched on Medium Anyone with an account could deface the site. The weakness is publicly readable. Task A1, this week, owned by AJ. Nothing else starts first.
Officers graduate and nobody knows the passwords High The site slowly dies — nobody can post events or fix anything. E5 handover note, E4 roster out of code, B6 roles instead of shared logins.
Events go stale High Directly undermines the credibility the whole site is built to establish. E1, and make posting an event part of the routine for every activity.
Another unreviewed change breaks the site Medium The site cannot publish — it already happened once, for about a day. A4 branch protection turns the process rule into an enforced one.
Everyone gets busy with exams High Work stops mid-way and context is lost. Keep tasks small and finishable. Milestone 1 is deliberately tiny.
Free hosting limits are exceeded Low The site slows or stops. Spam protection is already in place; A3 adds automatic cleanup. Set a budget alert.

One habit worth adopting. Keep this document and the tracker as the single source of truth, and update the tracker the moment something ships.

A finished feature marked "Not Started" cost this project real confusion — the Projects page was live while the tracker said work hadn't begun. Thirty seconds of updating saves an hour of asking.
